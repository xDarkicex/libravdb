## Part 1: The Research Response

The seven questions and their answers, as provided by the research agent.

### Q1: Leiden Partitioning and HNSW Traversal Cost

Standard HNSW traversal cost is `O(ef × log N × D)`, where each of the `log N` hops touches `ef` candidate neighbors of dimension `D`. Leiden partitioning splits this cost into two regimes because memory locality differs sharply between intra-community and inter-community hops.

The refined model is:

```
C_traversal = C_intra × N_intra + C_inter × N_inter
```

where `N_intra + N_inter = ef × log N` (total hops), and:

- `C_intra ≈ D × t_L1` — 7 vectors at 128-dim fit in a single cache-line-aligned page and reside in L1, with `t_L1` typically 1–4 cycles per access on modern x86
- `C_inter ≈ D × (p_TLB × t_TLB_miss + p_L2/L3 × t_L2/L3_miss + p_DRAM × t_DRAM)`, where the miss probabilities and corresponding latencies are on the order of 100–150 cycles (L3 miss) up to 60–100 ns (DRAM random access)

Because `C_intra` is bounded by L1 hit time (~1 ns) and `C_inter` is dominated by DRAM/TLB-miss latency (~90–150 ns), the intra/inter ratio lands in the **~50–150x range** rather than a flat 10x — closer to canonical Hennessy & Patterson cache-hierarchy latency gaps. The exact ratio is workload- and hardware-dependent, so a config-driven calibration step (measuring actual page fault rates at runtime) is more defensible than hardcoding a fixed multiplier.

### Q2: ECBB Pruning and Plan Enumeration

ECBB (bounding-sphere) pruning is a **macroscopic, coarse-grained** pruning law analogous to PLAID's centroid pruning — it eliminates a whole community/page before touching individual vectors.

Composability rules:

| Interaction | Behavior |
|---|---|
| ECBB + graph traversal | Pushable — any HNSW neighbor set fully contained in a rejected page can be pruned before expansion |
| ECBB + FVS (pre/post/in-filter) | Commutes with pre-filter; with post-filter, ECBB must run first; in-filter requires ECBB to be page-aware |
| ECBB + ApproxMaxSim upper bound | Layered, not composable into one bound — ECBB (macroscopic) then ApproxMaxSim (microscopic); apply ECBB first to shrink candidate pages, then ApproxMaxSim within survivors |

Col-Bandit reinforces this layering principle: it explicitly targets fine-grained (token-level) pruning on top of standard indices, positioning itself as orthogonal to coarser offline/index-time methods.

### Q3: MaxSim Cost Model Variants

Three cost regimes, using `L_q`, `L_d` = query/doc token counts, `D` = embedding dim, `K_c` = number of centroids, `N` = corpus size:

| Method | Cost Formula | Notes |
|---|---|---|
| Full/brute-force MaxSim | `O(N × L_q × L_d × D)` | Matrix multiply over all token pairs, all docs |
| PLAID-pruned MaxSim | `K_c × L_q × D` (centroid scoring) + `n_docs × L_q × L_d × D` (survivor full scoring), `n_docs ≪ N` | PLAID reports up to 45x CPU speedup vs. vanilla ColBERTv2 |
| HNSW-then-MaxSim | `ef × log N × D` (HNSW on single-vector proxy) + `n_cand × L_q × L_d × D` (MaxSim rerank) | Requires a proxy vector (e.g., mean-pooled or first-token embedding) |

**Crossovers:**
- PLAID-pruning wins once `K_c × L_q ≪ N × L_d` — empirically true since PLAID sets `K_c ∝ √(#embeddings)`, giving sub-linear scaling verified up to 140M passages
- HNSW-then-MaxSim beats brute-force MaxSim only when the single-vector proxy has high enough recall correlation with true MaxSim ranking; in practice this often fails for late-interaction models because MaxSim is inherently asymmetric and query-dependent

### Q4: Leiden/HNSW Layer Tradeoff

Given per-layer degree distribution `deg(ℓ)` and layer count `L`, define per-hop inter-page probability `ρ(ℓ)` — near 0 at layer 0 (co-located neighbors), rising sharply at upper layers where hubs span the whole graph.

- **Per-community**: minimizes `C_inter` at layer 0 but forces every upper-layer hop to pay `C_inter`
- **Per-layer**: optimal for upper-layer locality but destroys the L1-cache benefit at layer 0
- **Hybrid** (bottom 2 layers by community, upper un-co-located): approximates the optimum when `deg(ℓ=0,1)` dominates total traversal volume

The optimal policy is a function of the fraction of total hops occurring at layer 0/1 vs upper layers: hybrid wins whenever that fraction exceeds roughly 80–90%, which holds for most practical `ef` settings.

### Q5: Extending the Type Lattice with Matrix Types

Two constructors added to the existing lattice:

- **Fixed-shape**: `MATRIX(elem_type, dim_1, dim_2, ...)` — e.g., `MATRIX(FLOAT, 128, 32)` for a fixed 32-token document
- **Variable-length**: `MATRIX(elem_type, dim)` where `dim` is a value-level (row-count) variable bound at runtime

Type rule:
```
Γ ⊢ doc : MATRIX(VECTOR(D), L_d)
Γ ⊢ query : MATRIX(VECTOR(D), L_q)
─────────────────────────────────────
Γ ⊢ maxsim_score(doc, query) : FLOAT
```

The inner `VECTOR(D)` dimension must unify across both operands while `L_d`, `L_q` remain independent.

**Subtyping:** `MATRIX(T, m, n)` is a subtype of `MATRIX(T, dim)` (fixed-shape matrices are subtypes of the variable-length form). This mirrors Calcite's `ARRAY` and `MULTISET`, but differs in that the inner fixed-width vector constraint is preserved.

### Q6: Optimizer Plan Enumeration for the Hybrid Query

For a query filtering by `published_at`, a correlated `author IN (...)` subquery, and ranking by `maxsim_score`, four plan shapes emerge from the standard predicate-pushdown and join-reordering equivalence laws combined with the ECBB/PLAID pruning laws:

| Plan | Shape | Wins when |
|---|---|---|
| With-relational-filter first | Push `WHERE` clauses before any vector search | Filters are highly selective |
| HNSW-then-MaxSim | Single-vector proxy HNSW, then full MaxSim rerank | Proxy correlates well with MaxSim AND filters not very selective |
| PLAID-then-MaxSim | Centroid pruning, then full MaxSim | Large corpus, no reliable proxy, weak filters |
| Brute-force-MaxSim-with-pruning | Full scan with centroid-level pruning only | Filters are non-selective and cheap to evaluate post-hoc |

The equivalence laws generating these shapes: predicate pushdown, join-order swap (semi-join for `IN (SELECT...)` can be materialized early or late), and the ECBB/PLAID macroscopic pruning laws from Q2.

### Q7: Migration Cost Under Writes and WAL/Staleness Interaction

Per-migration cost: `O(D)` bytes (AVX-512 copy) + `O(1)` (CAS) + `O(N_page)` (ECBB bounding-sphere recompute), bounded by the configured migration rate and the worker's CPU budget.

- **WAL interaction**: each migration logged as a lightweight WAL entry recording `(vector_id, old_page, new_page)` for crash recovery without re-running full Leiden re-partitioning
- **Staleness detection**: the optimizer tracks a lag counter — the difference between writes committed and migrations applied — exposed as a metric; once lag exceeds a threshold (calibrated against the Leiden ΔQ stability bound), the partitioning is flagged stale
- **Plan preference under staleness**: when stale, the optimizer should prefer plans that are less sensitive to locality assumptions — e.g., falling back to PLAID/centroid-pruned brute-force MaxSim over ECBB-pruned page traversal, since ECBB's bounding-sphere disjointness test becomes unreliable when many vectors sit in transitional pages

## Part 2: Worked Examples

The research response provided two worked examples with explicit cost calculations.

### Worked Example 1: HNSW Traversal Cost Under Leiden Partitioning

**Parameters:** D=128, N=10M vectors, ef=100, latencies from Hennessy & Patterson cache tiers and PLAID's reported 92–142 ns memory-access measurements.

| Parameter | Value |
|---|---|
| `t_L1` | 1 ns |
| `t_TLB_miss` | 20 ns |
| `t_L3` | 15 ns |
| `t_DRAM` | 100 ns |
| `C_intra` | 128 ns |
| `C_inter` | 7,616 ns |
| **Ratio `C_inter / C_intra`** | **~60x** |

With `ef × log N ≈ 2,325` total hops and an 85%/15% intra/inter split (typical for a well-formed Leiden partition):

- Leiden-optimized traversal: **2.91 μs/query**
- Plain HNSW (no locality, mixed cache profile): **7.89 μs/query**
- **Speedup: ~2.7x**

The ~60x per-hop ratio is squarely inside the Hennessy & Patterson L1-vs-DRAM latency gap range (typically 50–150x on modern x86), not the flat "10x" rule of thumb.

### Worked Example 2: MaxSim Cost Model at PLAID Scale

**Parameters:** 140M passages, `L_q`=32, `L_d`=180, D=128 (ColBERTv2/MS MARCO setup, matching PLAID's published benchmarks).

| Method | Cost breakdown | Total latency |
|---|---|---|
| Full brute-force MaxSim | 140M × 32 × 180 × 128 ops | **~31,000 sec/query** (infeasible) |
| PLAID (`n_docs`=1024) | 52.1 ms centroid + 226.5 ms survivor | **278.6 ms** |
| HNSW-then-MaxSim (`n_cand`=1000) | 0.18 ms HNSW + 221.4 ms rerank | **221.4 ms** |
| HNSW-then-MaxSim (`n_cand`=100) | 0.18 ms HNSW + 22.1 ms rerank | **22.3 ms** |

The PLAID figure of ~279 ms lines up with the paper's own reported range of 92–352 ms end-to-end CPU latency. The dominant cost driver in both PLAID and HNSW-then-MaxSim is the **survivor/rerank stage** (`n × L_q × L_d × D`), not the initial candidate-generation stage — tuning candidate-set size is the highest-leverage optimization knob.

## Part 3: Critical Review

The research response is well-grounded. The cost formulas are derived from cited sources (Hennessy & Patterson for cache latencies, PLAID for MaxSim benchmarks, Leiden paper for community stability). The worked examples at PLAID's published 140M-passage scale calibrate against real numbers. But the response has caveats that need to land before the cost model ships.

### What's Strong

1. The **~60x per-hop intra/inter ratio** is correctly derived from cache hierarchy latencies. The accompanying ~2.7x total query speedup (from the 85/15 intra/inter split) is the right framing — the 60x is per-hop, the 2.7x is what the user actually sees.
2. The **PLAID latency at 140M passages** (278.6 ms) is inside the paper's published 92–352 ms range. Good validation.
3. The **ECBB composability table** is clean and matches the prior chunk's framing (macroscopic vs microscopic pruning layers).
4. The **matrix type extension** with fixed-shape vs variable-length forms is the right structure, and the inner `VECTOR(D)` dimension unification is correct.
5. The **plan enumeration for the hybrid query** identifies four plan shapes with clear win conditions. The "push filter first when selective" insight is right.
6. The **fallback-to-PLAID-when-Leiden-is-stale** recommendation in Q7 is the correct policy.

### What's Wrong or Under-Specified

1. **The HNSW-then-MaxSim 12x speedup is conditional on a strong assumption.** The research correctly notes that `n_cand=100` HNSW-then-MaxSim (22.3 ms) beats PLAID (278.6 ms) by 12x — but only if the single-vector proxy correlates with true MaxSim rank. For real ColBERT embeddings, this correlation is weak because MaxSim is inherently query-dependent and multi-vector. The 12x speedup is an *upper bound on a conditional claim*. In practice, HNSW-then-MaxSim often loses to PLAID for ColBERT-style embeddings.

2. **The `K_c` value is unspecified in the MaxSim cost formula.** `K_c × L_q × D` is the centroid scan cost, but `K_c` varies from ~1024 (small) to ~65536 (PLAID's typical) depending on the codebook. At `K_c=65536`, the centroid scan is `65536 × 32 × 128 = 268M ops` — comparable to the survivor scoring at 1024 docs. The cost formula needs `K_c` as a parameter with a typical range.

3. **The ApproxMaxSim upper bound correction is missing.** The prior review (`mvcc-hmgi-late-interaction-research-review-08-01-2026.md`, point 3.1) flagged that the centroid dot product is *not* a sound upper bound for the true MaxSim score because PLAID's 4-bit residuals are signed. The correct upper bound is:
   ```
   upper_bound = centroid_dot + L1_norm(residual_max) × L1_norm(query_token) / sqrt(D)
   ```
   The research response cites PLAID but doesn't include this correction. Without it, the pruning is unsound and the recall guarantee is broken.

4. **The cost model needs a staleness factor.** Q1 assumes the Leiden partitioning is up-to-date. Q7 says "fall back to PLAID when stale." But the cost model needs a continuous degradation: as the partitioning becomes stale, the intra/inter ratio degrades from 60x toward 1x (no benefit). The implementation needs a `staleness_factor ∈ [0, 1]` that the optimizer multiplies the intra-community benefit by.

5. **The Leiden migration cost isn't in the per-query cost model.** Q7 quantifies migration cost (O(D) copy + O(1) CAS + O(N_page) ECBB recompute), but this cost is amortized over many queries, not paid per query. The cost model should account for this amortization — the optimizer should prefer plans that don't trigger excessive migrations (e.g., plans that touch few Leiden pages).

6. **The matrix subtyping rule is incomplete for inner dimension mismatch.** The response says `MATRIX(T, m, n)` is a subtype of `MATRIX(T, dim)` and the inner `VECTOR(D)` dimension must unify. But it doesn't say what happens when the inner dimensions differ: `MATRIX(VECTOR(128), 32)` and `MATRIX(VECTOR(256), 32)` are *incompatible* because the inner dimensions don't unify. The subtyping rule needs to be: **width subtyping on the outer row count, invariant subtyping on the inner `VECTOR` dimension**.

7. **The 80-90% threshold for the hybrid Leiden/HNSW layer policy is empirical, not derived.** The response gives the threshold but doesn't say how to compute it. It should be: the fraction of total hops occurring at layers 0-1 vs upper layers, computed from the HNSW parameterization (M, ef, layer count). With M=16, ef=100, layer count ~ log(N), the layer 0-1 fraction is empirically ~85-95% on real workloads.

### The Biggest Gap: Integration with the Equivalence Law Catalog

The cost model is correct for individual components (HNSW traversal, MaxSim, ECBB pruning). But it doesn't integrate with the algebraic equivalence laws from the foundations doc. Specifically:

- **FVS pushdown law:** `topk(k, σ_p(R), d) ≈ σ_p(topk(k + c(sel(p), θ_GLS), R, d))`. The cost model should specify how the Leiden partitioning affects the oversampling factor `c`. If the filter is spatially concentrated (high `θ_GLS` in one community), the Leiden partitioning lets you skip other communities entirely, reducing the oversampling needed.
- **K-NN join reorder law:** `topk(k, R ⋈_E S, d) ≈ R ⋈_E topk(k × E[fanout], S, d)`. The cost model should specify how Leiden partitioning affects the fanout estimate. If the join is intra-community, fanout is small (7 nodes per page for 128-dim); if inter-community, fanout is large.
- **The four plan shapes from Q6 should be derivable from the equivalence laws**, not just listed as options. The laws say *when* each plan is correct; the cost model says *which is cheapest*.

This is the central integration problem. The algebra (foundations doc), the storage (CoW Slab, Leiden, MaxSim), and the cost model (this response) are three pillars. The optimizer is the keystone that holds them together. Without the integration, each pillar is correct in isolation but the optimizer can't reason across them.

## Part 6: Next Research Target

The biggest unaddressed gap is the **integration of the cost model with the algebraic equivalence laws**. The research has produced three pillars:

- The algebra and equivalence laws (`foundations-of-unified-query-algebra-08-01-2026.md`)
- The storage layer (`mvcc-hmgi-late-interaction-research-review-08-01-2026.md`)
- The cost model and plan enumeration (this doc)

What it hasn't produced is the **unified optimizer**: a single framework where the equivalence laws generate plan candidates, the cost model ranks them, and the Leiden partitioning, ECBB pruning, FVS strategies, and MaxSim are all integrated.

The next research target is the **unified optimizer specification**. It should produce a document that specifies:

1. **Plan generation:** How each equivalence law in the foundations doc generates a specific plan shape. The FVS pushdown law generates pre/post/in-filter plans. The K-NN join reorder law generates vector-first vs join-first plans. The graph predicate pushdown law generates graph-traversal plans with filters pushed into the pattern.

2. **Plan ranking:** How the cost model from this response ranks the generated plans. Per-operator cost formulas (with `K_c`, staleness factor, migration cost), combined into per-plan cost via the composition rules from Q2.

3. **The FVS-Leiden interaction:** How the Leiden partitioning affects the FVS strategy choice. If the predicate is spatially concentrated in one community, pre-filtering on the community (and running HNSW within it) is cheaper than post-filtering. The cost model should make this explicit.

4. **The MaxSim integration:** How the multi-vector cost model integrates with the single-vector cost model. For a query that has both a single-vector and a multi-vector component, the plan is: (a) generate candidates via single-vector HNSW with PLAID pruning, (b) rerank via MaxSim. The cost is the sum.

5. **Worked examples for the representative hybrid queries** from the foundations doc. Apply the unified optimizer to the worked example (compromised hosts connecting to servers via HTTPS with 90% accuracy target) and to the MaxSim hybrid query. Show the plan enumeration, the cost ranking, and the chosen plan.

6. **Validation against published benchmarks.** Compare the cost model's predictions against PLAID's published 92-352 ms latency at 140M passages. Compare against HNSW-only benchmarks on standard datasets (ANN-Benchmarks, LDBC SNB). The cost model should be within 2x of published numbers; if not, the model needs calibration.

7. **The ApproxMaxSim upper bound correction** (point 3 in the critical review) — apply the correction to the cost model, verify the pruning is sound, and re-derive the PLAID cost formula with the correction.

This is the bridge between the algebra, the storage, and the cost model. Without it, the optimizer is ungrounded. With it, the build can start Phase 8 (FVS strategy selection) with a cost model that knows about Leiden partitioning, multi-vector queries, and the algebraic equivalence laws.
